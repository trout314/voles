# Contributing

## Development setup

```bash
git clone https://github.com/trout314/voles
cd voles
pip install -e ".[dev,full]"
```

The `full` extra adds `numba`, which the array-based solvers use as a fallback
for collocation settings not compiled into the D extension. Without it those
tests are skipped (and the scalar fallback path raises `NotImplementedError`
at runtime), so install it for development.

## Building the D extension (required)

The D extension is a required part of the package. Tests will fail without it.

To build it you need [ldc2](https://github.com/ldc-developers/ldc/releases) and
[meson](https://mesonbuild.com/) + [ninja](https://ninja-build.org/):

```bash
pip install meson ninja
# add ldc2 to PATH, then:
meson setup dlang/build dlang --buildtype=release
ninja -C dlang/build
```

Use `--buildtype=release` — it is what CI and the published wheels use, and
meson's default (`debug`) is much slower.

Then copy the built library into the package:

```bash
# Linux
cp dlang/build/volterra_dlang.so src/voles/

# macOS
cp dlang/build/volterra_dlang.dylib src/voles/

# Windows (PowerShell)
Copy-Item dlang\build\volterra_dlang.dll src\voles\
```

Verify it loaded:

```python
import voles
print(voles.__version__)  # should print without ImportError
```

### LAPACK (optional)

LAPACK enables the `dgesv_` linear-solve path for vector equations with
runtime dimension (d > 8); a pure-D LU fallback covers the same functionality
without it. meson detects LAPACK only via pkg-config, and Homebrew's `lapack`
is keg-only, so on macOS:

```bash
brew install lapack
export PKG_CONFIG_PATH=/opt/homebrew/opt/lapack/lib/pkgconfig
meson setup dlang/build dlang --buildtype=release   # should report "dependency lapack found: YES"
```

Verify with:

```bash
python -c "from voles._dlang import have_lapack_d; print(have_lapack_d())"
```

### Compiled collocation settings

The D extension is compiled with template specializations for a fixed list of
collocation settings `(divs, choices)` (used by `quadrature="collocation"`;
`voles._dlang.supported_coll_settings_d()` lists them) and for vector
dimensions d ≤ 8 (larger d uses a runtime-dimension driver). Widening those ranges means editing the
`max_coll_divs` / `max_coll_params` / `max_d_compile` enums in
`dlang/source/volterra_solvers.d` and recompiling — compile time and binary
size grow quickly, which is why the ranges are modest and the Numba fallback
exists for scalar equations.

## Running tests

```bash
pytest tests/ -v
```

pytest runs with `filterwarnings = ["error"]` (see `pyproject.toml`): a test
that triggers a warning fails unless it expects it (`pytest.warns`) or filters
it. Until 1.0 the 0.10 API's deprecation messages are ignored there, so the
legacy tests keep running.

`tests/test_public_api.py` pins `voles.__all__` and every public signature
against `tests/data/public_api.json`. After an intended API change, run
`python tests/test_public_api.py --update` and review the diff.
`tests/test_typing.py` type-checks the documented calls in
`tests/typing/public_api_usage.py` with mypy (part of the `dev` extra).

The Examples sections of the public docstrings are run by
`tests/test_docstring_examples.py`; print rounded values in them so the output
is the same on every platform.

The Python code blocks in `docs/` and `README.md` are also executed in CI to
keep the examples working. Run them locally with:

```bash
pytest --markdown-docs docs/ README.md
```

(`pytest-markdown-docs` is included in the `dev` extra.)

## Documentation

The documentation site is built with MkDocs (Material theme); the API
reference pages under `docs/api/` are mkdocstrings stubs that pull in the
docstrings from `src/voles/`, so API docs are edited in the docstrings
themselves. Docstrings are numpydoc style. A `See Also` section is plain
Markdown: write links as `[solve_vie2][voles.solve_vie2]` (bare names are not
linked). The user guide (`docs/guide/`) holds the conventions, warnings,
migration and stability pages. To preview locally:

```bash
pip install -e ".[docs]"
mkdocs serve
```

The site is deployed to GitHub Pages by CI on pushes to `main`. The
benchmark tables in `docs/benchmarks.md` are regenerated by the benchmark CI
job — don't edit the content between the marker comments by hand. The
benchmark names in `benchmarks/bench_solvers.py` key the published history:
keep them when changing what a benchmark calls. The
install section of `README.md` is the canonical copy and is pulled into the
docs via a snippet; edit it only in the README.

## Submitting changes

- Open an issue before starting significant work
- Keep pull requests focused on a single change
- Ensure `pytest tests/ -v` passes before submitting
- Add an entry to the `[Unreleased]` section of `CHANGELOG.md` (Keep-a-
  Changelog style: `Added` / `Changed` / `Fixed` / `Performance` /
  `Documentation`)

## Releases

The version lives in one place, `__version__` in `src/voles/__init__.py`
(`pyproject.toml` reads it from there). Wheels are built and published by CI
when a version tag (`v*`) is pushed.
Only wheels are published (no sdist), since building requires a D compiler.
